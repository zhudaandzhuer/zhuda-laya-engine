# 遊戲視覺開發規則：先驗 Prefab，再組 Scene

適用於消費專案新增或修改的 UI、角色、模型、Spine、材質及特效。交付單位是**能用穩定 ID 單獨載入、重現狀態、與來源比對的 Prefab**。例如同一個金額牌在預覽和遊戲裡必須來自同一份定義。改字級或換貼圖後，下一位 agent 能直接叫出那塊牌的文字節點驗收。

## 五個關卡

| 順序 | Agent 要交付什麼 | 何時能往下走 |
| --- | --- | --- |
| 1. 盤點來源 | 為貼圖、圖集、模型、字型等建穩定的邏輯 ID，記錄來源版本、預期外觀、規格與用途。指定比較基準、測試狀態與容差。 | 另一人能指出「哪張圖、哪個狀態、哪個尺寸」代表正確。缺參考的項目保持待驗。 |
| 2. 製作 Prefab | 在遊戲庫存放可版本控制的 Prefab 定義。標明依賴 ID、根節點、可檢查子節點的穩定路徑、尺寸／錨點／內容區、可注入的狀態與釋放責任。 | 獨立入口能讀同一份定義，僅靠測試資料、引擎和必要依賴完成掛載與拆除。 |
| 3. 單節點驗收 | 在獨立畫布選 Prefab、節點路徑、狀態與時間，實際繪製。保留必要的父變換、遮罩、材質或燈光；可隱藏無關同層節點。保存本次實圖、預期圖、差異與量測。 | 要求的節點／狀態都通過，結果綁定到目前版本。缺圖、過期、超差、畫不出或設備無法驗證，均須記錄。 |
| 4. 由小到大組裝 | 先把已驗的子 Prefab 組成可獨立預覽的面板／角色，再把通過的組合實例化到 Scene。Scene 負責位置、層級、燈光、輸入路由與資料綁定。 | 組合在隔離預覽中通過，且 Scene 引用相同 ID、版本與建立路徑。進入 Scene 前，該範圍必需的隔離證據須為 PASS。 |
| 5. 獨立遊戲整合 | 用固定引擎版本建置遊戲，測真實輸入、跨元件遮擋、縮放／DPR、狀態更新與拆除。對有平台差異的行為另跑目標裝置。 | 場景證據與單節點證據分開保存。每項結果附實際環境與重跑方式，未測項保留 UNAVAILABLE。 |

一張 PNG 可以是多個 Prefab 的依賴。需要被重用、換皮或單獨驗收的組件要有自己的 Prefab ID。其內的文字、邊框等可以用穩定的子節點路徑選取，無須為每個像素元件建立檔案。優先使用適用的序列化格式，例如 UI 階層的 `.lh`。程序網格、粒子、可變數量清單可以用具名、可序列化的配方加上型別化 renderer；配方仍是 Prefab 的來源，並接受相同的隔離驗收。重複 30 格時，Scene 可以配置 30 個實例並注入不同資料。

### 驗收記錄範例

下表是交付格式範例，值由消費專案提供。建立者須填入在乾淨 checkout 可執行的命令或本機預覽連結。僅有整場遊戲的入口不符合第 2 關。

| 欄位 | 以數字牌為例 |
| --- | --- |
| 定位及版本 | Prefab ID `ui/amount-plate`，子節點 `value`，資料及貼圖版本、字型版本、引擎 SHA、遊戲 SHA |
| 比較條件 | 一組短值與一組長值；指定字型、locale、字型就緒時點、viewport、DPR、狀態、seed 與動畫取樣時間 |
| 預期 | 指定素材參考及文字可用矩形；字形連同描邊不得越界，四角、透明區與錨點按參考比對 |
| 重現與產物 | 單獨開啟此 ID／節點／狀態的命令、預期與實際畫面、差異圖、幾何量測、容差、PASS／FAIL／UNAVAILABLE、失敗原因 |
| 生命週期 | 載入時關閉、缺檔、逾時、重試與釋放；涉及資源所有權者記錄 30 次載入／卸載後的計數 |

資產、字型、Prefab 定義、renderer 或其依賴更新後，將受影響的單節點與父組合標為待重驗。先用既有基準重跑；設計確實改版時，將新舊參考、差異與採用理由一起交付。Scene 內發現子節點跑版時，回到其 Prefab 重現並修正，再循序組裝。禁止用 Scene 專屬偏移掩蓋子節點的錯誤。

## API 與證據邊界

Checker 的 viewport／DPR 實測、schema 2 證據遷移，以及預覽／Scene 共用
`createAssetProvider` 的設定見[consumer tooling](consumer-tooling.md)。
舊 schema 1 報告不能直接改版號重用；需重新測量。

- 隔離預覽與消費端入口的 HTML 都要在腳本前宣告 `<meta charset="utf-8">`。Consumer build 會在輸出頁補上缺少的宣告；來源仍應明確寫出它。這固定瀏覽器字型測量的編碼環境，避免同一個 Label 在預覽和 Scene 產生不可重現的首幀差異。
- 遊戲固定公開套件版本或 Git SHA，使用獨立 consumer build 與嚴格型別檢查。先查已安裝版本的公開宣告、既有元件及測試。禁止複製或直接匯入引擎內部原始碼、修改 vendor，或用 `declare const Laya: any` 繞過型別缺口。
- 優先重用適用的 ZhudaUI／Laya UI 控件、切片與容器。特殊外觀可在遊戲的 Prefab renderer 組合公開的 Sprite、Label 或其他型別。採用自訂 adapter 時，在任務記錄寫明既有能力、缺口、作用範圍與可重現測試。可重用的引擎缺陷應帶最小失敗案例回報至引擎庫。
- 依賴 ID 走 AssetProvider 與既有快取／lease。時間、事件去重、輸入清理與資源釋放接既有生命週期。數值、派彩、網路權威、特效內容與媒體由遊戲持有。詳見[資產規則](asset-loading.md)與[獨立接入契約](3d-integration.md)。
- 靜態 schema、套件型別、單節點畫面、Scene 行為、裝置表現各記各的結果。禁止用固定為真的斷言、搜尋程式字串、截圖檔案大小、引擎示例通過或桌面模擬冒充遊戲實測。視覺檢查須能在刻意換錯貼圖、推歪文字或破壞透明度時報錯。

## 給消費專案的導入文字

安裝含此政策的引擎版本後，把以下段落納入**遊戲根目錄**的 `AGENTS.md` 或該工具會讀取的專案規則。引擎套件內的規則不會自動成為所有工具的專案指令。

> 視覺工作依固定引擎版本的 `docs/prefab-workflow.md` 執行。先建資產清單和 Prefab，在隔離入口按 ID、子節點及狀態比對來源，提交可重跑的證據，通過後才組面板和 Scene。遊戲與預覽共用同一份定義。FAIL、UNAVAILABLE 或過期證據不得放行對應階段。使用公開型別和資源生命週期；發現缺口時附最小案例。接手舊 Scene 時從下一個要改的元件開始，逐一建立 Prefab、比對後替換舊節點。

有 MCP 的 agent 呼叫 `get_agent_contract`，查看 `visualWorkflow`。沒有 MCP 時直接讀安裝套件的這份文件。消費專案須在自己的規則填上實際預覽命令、素材與基準位置、CI 任務及目標裝置。現有引擎工作台只示範內建資產。遊戲現階段需提供獨立測試入口，通用預覽與 CI 規畫見[工具路線圖](plans/prefab-toolchain.md)。
## 即時小窗預覽

消費專案完成 `prefabPreview` 設定後，可用引擎內建的 watch server：

```sh
zhuda-laya-watch --project /absolute/path/to/consumer --host 127.0.0.1 --port 8890
```

它先執行一次完整 consumer build，再監看 `src/`、`assets/`、`public/`、
`zhuda.config.json` 與 `package.json`。開啟輸出的 `prefab-preview.html` 或
`index.html` 後，儲存 Prefab、貼圖、定義或 Scene 變更會觸發重新建置；成功時
兩個頁面都自動重新載入，失敗時保留上一個可用輸出並在頁面 alert 顯示錯誤。
這是開發期預覽能力，仍須使用 `zhuda-prefab-check` 和 Scene 驗收報告作為
提交門禁。
