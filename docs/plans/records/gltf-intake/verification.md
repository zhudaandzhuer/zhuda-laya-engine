## Measured: the embedded-picture path

`big-picture.glb` holds one 2048 by 2048 PNG of 10.4 MB. Five rounds each,
alternating; the script asks the page for its JavaScript heap
(`Runtime.getHeapUsage`) every few milliseconds while a load runs and after a
forced collection when it ends. Times include fetching the file over loopback.

| Median of 5; range over three runs | LayaAir `glTFResource._parseglb` + `create()` | Engine `ZhudaModelLibrary.instantiate` |
| --- | --- | --- |
| Time, WebGL | 336.8–372.8 ms | 69.7–77.6 ms |
| Time, WebGPU | 303.3–316.8 ms | 49.2–50.1 ms |
| Sampled heap peak above the start, WebGL | 334.5 MB | 0.13–0.22 MB |
| Sampled heap peak above the start, WebGPU | 334.5 MB | 0.23–0.28 MB |
| Heap kept while the model lives (after collection), WebGL / WebGPU | 20–28 / 24–36 KB | 31–32 / 27–40 KB |

Asserted, with wide margins so that a regression fails the script: the same
picture; the engine's median time below LayaAir's; the engine's sampled peak
under a tenth of LayaAir's. The values in the table are measurements, not
thresholds.

The peak comes from LayaAir's `Base64Tool.encode`, which builds the data URL
one character at a time (about 14 million concatenations for this picture).
Neither path keeps it: the retained heap is the same within noise. The heap is
sampled between the page's tasks, so a peak inside one synchronous task could
be missed; these are lower bounds of the peak. The decoded picture's own
memory (outside the JavaScript heap) is not measured; GPU memory is counted
only as textures and their estimated bytes, above.

The first round reported LayaAir's peak as 292.7 MB. That page destroyed
LayaAir's own model without waiting for LayaAir to retire its renderers, which
left the native texture alive between rounds; its first round of five showed
334.5 MB and the other four 292.7 MB. The page now draws a frame between
destroying the tree and the resource, the native side leaves nothing behind,
and every round shows 334.5 MB. Why the leftover lowered the later samples was
not investigated.

## Review round 1

A reviewer ran the first round's code in a browser and in Node. What was found
and what was done:

1. **A picture used by several material slots was decoded and uploaded once
   per slot** (major). LayaAir asks for a texture once per slot; its data URL
   was the same for the same bytes, so its URL cache answered the repeats. A
   Blob URL is new each time. The reviewer measured 4 textures and 21.3 MB
   where LayaAir kept 1 and 5.33 MB (four materials on one picture), and 3
   against 2 for a packed occlusion/metallic-roughness picture. Fixed in
   `Laya342GltfAdapter.ts`: a repeat is recognised by its type and bytes
   during the parse and gets the first load's texture; the bytes kept for
   that are let go when the textures have loaded. Evidence: the two "shared"
   rows and counts above on both backends; unit test "one embedded picture
   makes one texture". As in LayaAir, a picture shared by slots with different
   samplers or colour spaces has the first slot's (not changed here; see
   Limits).
2. **A probe timeout was remembered as "this device cannot decode"** (major).
   With the main thread busy for about three seconds while the first probe
   was pending, the wall-clock timer ran before the picture's load event and
   `{webp: false, avif: false}` stayed for the page. Fixed in `GltfIntake.ts`:
   the deadline counts thirty turns of the event loop instead of three seconds
   by the clock, so a busy thread delays both alike; only a decoder's own
   answer is remembered; a decoder that still gives none is listed in
   `unanswered`, counted as no for that load only, reported as
   `IMAGE_DECODE_UNANSWERED`, and asked again by the next call. Evidence: the
   busy-thread assertion above on both backends (the first round's build
   failed it); unit tests "a decoder that gives no answer is not remembered"
   and "a main thread busy past the deadline" (the latter also shows one
   wall-clock timer of the same length failing).
3. **The report said `supported` for integer vertex attributes in an external
   buffer, and the load threw a bare error** (minor). The report now says
   `EMBEDDED_BUFFER_REQUIRED` (an error), so the file is refused by
   `ZhudaModelCompatibilityError` with that code before any parse. What only
   the bytes show (an accessor past its view) is refused with the report plus
   `INVALID_DOCUMENT`. A `.gltf` with a separate `.bin` and normalized
   texture coordinates is still refused where it used to load and draw wrong:
   fetching outside buffers for the dequantize pass was not added.
4. **A node naming a light or camera the file does not have was dropped
   silently** (minor). Now `INVALID_LIGHT` / `INVALID_CAMERA` at the node's
   path, and the file is `degraded`.
5. **The failed-load unit test used a loader that rejects; LayaAir's resolves
   null and keeps a null in its URL cache** (minor; read from vendor code by
   the reviewer, not run). Run here with a PNG that does not decode: LayaAir's
   own parse does leave that null, under its data URL. The engine now loads
   embedded pictures with `cache: false` and leaves nothing (measured; the
   first round's code was not run against that file). The unit test's loader
   answers as LayaAir's does (a rejecting loader is still covered, named as
   such), and the texture that did not load is in the model's report
   (`IMAGE_DECODE_FAILED`, `degraded`) instead of only on the console.
6. **Claimed behaviours that were never drawn** (minor). Now drawn on both
   backends: the orthographic branch of `applyZhudaGltfCamera`; AVIF preferred
   over WebP; the fallback path through the real adapter (with the device's
   answer given by hand, `ModelLibraryOptions.imageDecode`); pictures shared
   between slots; the cycle loop with lights and a WebP picture. The
   embedded-picture time and heap now fail the script if they regress past
   wide margins.

Also found while doing this:

## Lifecycle and failure cases

Unit tests (`tests/gltf-intake.test.mjs`) cover:

- Meshopt: KHR name with COLOR and OCTAHEDRAL filters decodes to the
  encoder's bytes (positions and texture coordinates exact, colours within
  one 8-bit step); COLOR under the EXT name, COLOR with a 12-byte stride, both
  names on one view and an unknown filter are refused; `DECODER_REQUIRED` is
  an error when required and makes the file `degraded` when optional.
- Dequantizing: values through the node transform match the float file
  within 2e-5 m; normalized signed values clamp at -1; integer values stay
  whole; sparse values are applied; a `.gltf` with data-URI buffers comes out
  as a GLB; the embedded picture's bytes survive; node transforms are
  unchanged; `KHR_mesh_quantization` leaves the declarations; Meshopt then the
  pass gives the same floats as the pass alone. Refused: an unsigned 32-bit
  POSITION (also `INVALID_DOCUMENT` in the report), a wrong TEXCOORD type,
  external buffers (`EMBEDDED_BUFFER_REQUIRED` in the report; a float file
  with an external buffer is not flagged), an accessor reading past its view,
  falling sparse indices, an output over budget, an invalid budget.
- WebP/AVIF: the source order (AVIF, WebP, fallback) for each device answer;
  `IMAGE_DECODE_UNAVAILABLE` as error without a fallback and as a degrading
  warning with one; `IMAGE_DECODE_UNANSWERED` the same way when the decoder
  gave no answer, and nothing when another offered image loads;
  `IMAGE_DECODE_UNCHECKED` without a device answer; the inventory's WebP/AVIF
  images; a resource refuses a texture with nothing decodable before loading.
- Embedded pictures: they reach the Laya loader as a Blob URL with their MIME
  type, bytes and `cache: false`, revoked after the load; four materials on
  one texture load once and every slot takes its reference; colour plus a
  packed picture loads twice; two images of the same bytes are one picture;
  the same bytes under another type, or other bytes of the same length, are
  not; views that do not start on a word boundary compare correctly; a

  picture the loader answers with null (as LayaAir does) is tried once for

- The probe: yes, a decode error and a picture of the wrong size are each

## Limits and decision

- Phones, mini-game hosts, Safari and Firefox: not run. AVIF decoding in
  particular varies by device. The fallback and refusal paths are drawn only
  with the device's answer given by hand; desktop Chrome decodes both formats.
- A decoder that really gives the probe no answer was not met. That path is
  unit-tested with a stand-in image element, and reported through a library
  given the answer by hand. On a host where it happens, each model that needs
  the format waits out the probe (about 3 s on an idle thread) and loads its
  fallback or is refused, until the decoder answers. A model loaded in that
  state keeps its fallback picture while it stays in the library's cache; its
  report says so.
- The probe's deadline is thirty timers of 100 ms. A thread kept busy in
  thirty separate stretches, each ending just as a timer is due and before
  the picture's load event runs, would still read as no answer. Not met; the
  answer is then not remembered.
- One picture, one texture: as in LayaAir, a picture used by slots with
  different samplers or colour spaces has the first slot's settings. This is
  LayaAir's behaviour for external pictures too and was not changed. The
  repeat is recognised by comparing bytes, once per repeated slot; the cost of
  that was not measured apart from the whole load.
- A picture that does not decode leaves its material slots empty, as in
  LayaAir (the quad draws white). The report says so; nothing is substituted.
- Dequantizing raises GPU vertex memory back to float; GPU memory is not
  measured beyond texture counts and estimated texture bytes.
- A quantized file whose buffers are outside the file is refused
  (`EMBEDDED_BUFFER_REQUIRED`).
- An embedded picture's texture keeps a revoked Blob URL as its LayaAir URL and
  is not in LayaAir's URL cache, so LayaAir cannot fetch it again by URL (the
  data URL allowed that). Whether anything needs that, such as recovery from a
  lost GPU context, was not tested.
- Light units: the draw shows the engine makes the lights the documented
  mapping describes, on the right nodes and directions. It does not show the
  mapping matches three.js or a DCC render; LayaAir's falloff is not the
  inverse square, and with a file range the two differ by up to about 2x
  between a quarter and three quarters of the range.
- An orthographic camera takes its height from `ymag` and its width from the
  viewport; a file whose `xmag`/`ymag` is not the viewport's aspect ratio was
  not drawn.
- No light casts a shadow from the file; multiple scenes are not built
  (LayaAir builds the default scene).
- All fixtures are generated in code; no seller or Blender-exported file was
  loaded.
- WP4 items not done: `EXT_mesh_gpu_instancing`, texCoord 1 for AO/lightmap
  slots, Meshopt `useWorkers`.

Decision: **Implemented within scope**. Desktop WebGL and WebGPU verified; the
missing device and browser checks keep it from Accepted.
