# 豬大打鼓

原創的四軌節奏遊戲，兩首歌、各兩種難度。用同一個倉庫裡的 zhuda-laya-engine 的 2D 做，用來驗引擎的聲音在「必須跟音樂對準」時夠不夠用。

```
npm run verify            # 建置、型別、體檢、5 個測試
index.html?song=2&hard=1&auto=1
```

操作：音符落到線上時按 D F J K，或點那一軌；Esc 暫停。選單可以調聲音校正（±10 毫秒一格）。

## 做了什麼

- 歌是資料（速度、小節、有種子的旋律、低音、鼓）。每個不同的音用引擎的 `renderZhudaSynth` 算一次，遊戲自己混成一條單聲道 22050 Hz 的音軌，用 `encodeZhudaWav` 包成 WAV，經 `ProceduralAssetProvider` 當一個 sample 播。專案裡沒有任何音檔。
- 譜面取自旋律的起音（輕鬆只取正拍），所以譜和音樂一定同一個零點。
- 判定：±50 毫秒完美、±100 不錯、±140 勉強，過了算漏掉；一次按鍵只判那一軌最早的那個音。
- 打完會告訴你平均早或晚幾毫秒、校正該怎麼調。

## 查過什麼

| 項目 | 結果 |
| --- | --- |
| `npm run verify` | 體檢 HEALTHY，5 個測試過 |
| 真的按鍵（無頭 Chromium，`tools/play.mjs`） | 照頁面公布的時間按 54 個音：54 個完美，平均偏 −5 毫秒；中途按 Esc，歌的時間停住，按「繼續」後打完（`docs/evidence/keys.log.json`） |
| 機器準點打第二首認真 | 113 個音全完美、S（`docs/evidence/bot.log.json`） |
| 頁面內混音時間 | 37 秒的歌 110 毫秒、39 秒的歌 44 毫秒（無頭、軟體環境） |

## 沒查的

- **沒有人聽過**。歌是照樂理規則產生的，好不好聽、鼓和旋律有沒有對在一起，只有測試確認了第一拍在時間零有聲音。
- **聲音和畫面有沒有對準，沒有量過**：無頭瀏覽器沒有喇叭。按鍵測試驗的是「頁面時鐘 → 判定」這一段，不是「耳朵聽到 → 判定」。
- 真機觸控、藍牙耳機延遲、手機幀率，都沒有試。
- 長時間播放時頁面時鐘和音訊時鐘的漂移沒有量（40 秒的歌預期很小，但沒有數字）。

## 對引擎的發現

1. **沒有音訊時鐘**。`IframeSoundAdapter` 把唯一的 `AudioContext` 藏起來，`playSample` 只回傳 boolean：不知道聲音何時開始、現在播到哪。節奏遊戲只能用頁面時鐘；頁面失焦時引擎會自己暫停音訊而頁面時鐘繼續走，兩邊就錯開。→ 引擎現在有 `getSamplePositionSec(id)` 和 `getOutputLatencySec()`（`docs/audio.md`）；這個遊戲在歌響著的時候跟它對時：無頭 Chromium 的 AudioContext 裡一首歌讀了 1,315 次，和頁面時鐘最多差 10.2 毫秒，瀏覽器回報的輸出延遲是 32 毫秒。沒有解鎖聲音（沒有任何點擊或按鍵）或靜音時讀不到，退回頁面時鐘。
2. 靜音時 `playSample` 直接不播（回傳 false），所以靜音狀態下更不能拿「聲音有沒有在播」當時鐘。
3. 合成器一個 recipe 上限 10 秒、16 層：做不出一首歌。繞法是逐音算、自己混（本專案 `mix()`，約 0.1 秒）。`renderZhudaSynth` 和 `encodeZhudaWav` 都是公開的，夠用；文件沒有提這個用法。
